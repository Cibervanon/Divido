1.2 — Usuarios y concurrencia

  • Instancia API (Render Starter: 512 MB · 0,5 vCPU compartida): Fastify en un solo proceso Node sostiene ≈ 150–300 req/s de JSON simple (p95 < 50 ms). Con validación Zod + bcrypt puntual + pool pg, el throughput útil baja a ≈ 100–200 req/s.
  • Con un patrón de uso social (un usuario activo genera 5–10 req/min), eso equivale a ≈ 300–600 usuarios concurrentes activos cómodos. Por encima de ≈ 1.000 CCU aparecen colas en el event-loop y p95 > 500 ms.
  • Postgres (Supabase): el cuello real no será CPU sino conexiones: plan gratuito admite pocas conexiones directas; el pool de pg debe dimensionarse (recomendado 5–10) y usar el pooler PgBouncer de Supabase al escalar.
  • Miembros por grupo: el algoritmo de liquidación calcula transferencias mínimas explorando pares (O(m²)) y la UI pinta matriz/máscaras por miembro. Fluido hasta ≈ 20 miembros; a partir de 50 el recálculo y el DOM se notan en móviles gama media.

Pares evaluados por liquidación:

Con m = 6 miembros: 15 pares. Con m = 30: 435 pares (×29 más cómputo y celdas). El coste crece cuadráticamente: por eso el límite recomendado antes de ralentización perceptible es ≤ 20–30, y la fila roja ilustra el bloque que domina cuando m crece.

Evaluación del sistema: fortalezas

Áreas bien optimizadas en el estado actual — con evidencia de código
✅ Procesamiento en cliente

Descarga de CSV contable e informe PDF generados desde la memoria del navegador (Blob + BOM + csvEscape), además de export JSON completo para GDPR/baja de cuenta. Cero carga extra en la API y coste de servidor plano aunque crezca el uso.

Evidencia: apps/web/src/pages/group/BalancesTab.tsx:116–258 · ProfileModal.tsx:208
✅ Reactividad y feedback visual

Mutaciones TanStack Query con invalidación quirúrgica por queryKey y cancelQueries antes de escribir: evita respuestas fuera de orden (race conditions). Botones bloqueantes/estado «guardando» impiden doble envío. Caché server-side de balances amortiza el recálculo.

Evidencia: useGroupDetail.ts:72–86 (cancel + invalidate encadenadas) · apps/api/src/balanceCache.ts
✅ Modelo relacional completo

16 tablas normalizadas con separación clara: users ↔ group_members (incluye miembros fantasma is_ghost), groups, expenses + expense_participants (split exacto), payments, common_pot_contributions (bote) y audit_log inmutable.

Evidencia: apps/api/src/db.ts (DDL con CREATE TABLE IF NOT EXISTS)
✅ Hallazgos positivos adicionales

• Índices ya creados incl. compuestos (group_id, created_at DESC), (group_id, payer_id), parcial de notificaciones no leídas.
• N+1 eliminado: alta de gastos transaccional y consultas batch.
• Code-splitting por ruta: bundle inicial 393 → 215 KB.
• Algoritmo de liquidación verificado con 800 escenarios de tests de propiedades.
• El audit log ya está paginado (LIMIT/OFFSET).

Evidencia: db.ts:305–328 · commits 0e81afa, 8785924, a484c06 · routes/groups.ts:164–176

Auditoría de cuellos de botella

Qué fallará primero al aumentar la carga — severidad, síntoma y umbral de fallo
⚠️🛑 ALTA — Renderizado en DOM

La lista de gastos y el historial de actividad (group_events) se renderizan completos, sin paginación ni virtualización. Cada tarjeta ≈ 25–35 nodos DOM: 800 gastos ≈ 25.000 nodos → INP móvil > 500 ms. Además, el feed de eventos crece ×4–6 por cada gasto (creado, comentario, edición, pago): es lo primero que explotará. El patrón de paginación ya existe para audit_log; falta replicarlo.

SíntomaScroll con saltos, tipeo entrecortado en móvil
Umbral> 200 registros se nota; > 800 inutilizable en gama media
GroupPage.tsx (~2.800 líneas) · hooks ["expenses", groupId] sin LIMIT en API
⚠️ MEDIA — Indexación de BD

Buenas noticias: los índices críticos ya existen ((group_id, created_at DESC), (group_id, payer_id), (group_id, category)), así que los filtros y el ORDER BY no harán seq scans. El hueco real: sin paginación, el índice acelera el orden pero igualmente se serializa el grupo entero en JSON. Falta índice (group_id, created_at DESC) para group_events (hoy solo idx_events_group(group_id)) y revisar planes con EXPLAIN ANALYZE al superar 100k filas.

SíntomaPayloads MB-scale; latencia crece lineal con el histórico
Evidencia: db.ts:307,313,321–323 vs. endpoints de listado sin LIMIT
⚠️ MEDIA — Caché y re-fetch

No hay staleTime configurado: TanStack Query usa staleTime=0 por defecto, así que cada vuelta a la pestaña/ventana re-pide gastos, miembros y balances (refetchOnWindowFocus). En grupos grandes esto multiplica peticiones redundantes. Mitigación barata: staleTime: 30–60 s + placeholderData: keepPreviousData en filtros, manteniendo las invalidaciones actuales tras mutaciones (esas sí deben seguir forzando frescura).

SíntomaSpinners al volver a la app; tráfico ×3 innecesario
Evidencia: useGroupDetail.ts (queries sin staleTime explícito)
⚠️ ALTA — Seguridad y RLS

La regla «usuario fantasma no puede ser admin» y toda la autorización se aplican solo en la capa API (requireAdmin + check is_ghost): correcto y centralizado, pero la BD conecta con un único rol privilegiado, sin RLS nativa de Supabase como segunda línea. Si alguna ruta nueva olvida el middleware, la BD no opone resistencia. Acción: auditoría periódica de rutas con test que recorra todos los endpoints validando 401/403, y valorar RLS defense-in-depth si algún día se consulta desde cliente.

Síntoma potencialEscalada de privilegios por ruta olvidada
Evidencia: routes/groups.ts (check is_ghost) · plugins.ts (requireAdmin)
🔎 Deuda técnica menor detectada: GroupPage.tsx supera las ~2.800 líneas (monolito de UI). No impacta en runtime gracias al code-splitting, pero encarece mantenimiento y aumenta riesgo de regresiones. Candidato a dividir por tabs (Gastos / Balances / Actividad / Bote).

Roadmap de optimización y escalabilidad

Priorizado por relación impacto/coste — pensado para escalar manteniendo bajos los costes de servidor
PrioridadAcciónImpacto esperadoEsfuerzo
P1 🔴 Paginación server-side de gastos y eventos (LIMIT/OFFSET + cursor por created_at) replicando el patrón existente en audit log; botón «cargar más» en UI. Elimina el cuello nº1; payloads constantes (< 100 KB) sea cual sea el histórico. Coste servidor plano. Medio (2–3 d)
P1 🔴 Ajustar caché cliente: staleTime 30–60 s en gastos/miembros/balances + keepPreviousData en filtros; conservar invalidaciones post-mutación. −60/70 % de peticiones redundantes; UX sin spinners al alternar pestañas. Bajo (½ d)
P1 🔴 Test automatizado de autorización: barrido de todos los endpoints verificando 401/403 para anónimo, miembro no admin y ghost (incluye regla ghost-no-admin). Cierra el riesgo de omisión de middleware en rutas futuras; red de seguridad de la capa API. Bajo (1 d)
P2 🟡 Virtualización opcional (react-window) o render incremental si algún grupo opera sin paginación activada; índice group_events(group_id, created_at DESC). DOM acotado (< 2.000 nodos siempre); feeds fluidos con miles de eventos. Bajo–medio (1 d)
P2 🟡 Export server-side condicional: endpoint con streaming CSV solo cuando el volumen supere ~50k filas; mantener export cliente como vía rápida por defecto. Exportaciones gigantes sin bloquear el navegador; API solo paga cuando hace falta. Medio (1–2 d)
P2 🟡 Pooler y dimensionado de conexiones: pool pg 5–10 + PgBouncer de Supabase; monitorizar conexiones antes de subir réplicas. Evita agotamiento de conexiones al crecer instancias; requisito previo a escalar Render verticalmente. Bajo (½ d)
P3 🟢 Dividir GroupPage.tsx en módulos por tab + tests de integración ligeros. Mantenibilidad y velocidad de desarrollo; sin cambio runtime. Medio (2–3 d)
P3 🟢 Observabilidad básica: métricas p95 por ruta, logs estructurados y alerta de tamaño de BD al 70 % del plan. Detectar degradación antes que los usuarios; datos reales para sustituir estimaciones. Bajo (1 d)
P3 🟢 Load-test de referencia (k6) con perfil realista para fijar los números de esta ficha como SLA medidos, y particionado por created_at si se cruzan los 5M de gastos. Capacidad demostrable; plan de crecimiento de BD definido de antemano. Medio (1–2 d)
🎯 Estrategia de costes: las acciones P1 son casi gratuitas en servidor (menos payload, menos peticiones, tests locales) y compran meses de escala en los tiers base. Ninguna acción requiere migrar de proveedor: Vercel + Render + Supabase aguantan holgadamente hasta decenas de miles de gastos activos si se aplica este roadmap.
