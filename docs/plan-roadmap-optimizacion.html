Plan de Implementación — Roadmap de Optimización y Escalabilidad

Divido · cómo ejecutar las acciones P1/P2/P3 de la ficha técnica, en orden, con criterios de aceptación verificables
v1.0 · 22 ago 2026 3 sprints · ~3 semanas

Basado en docs/ficha-tecnica-divido.html. Cada tarea indica archivos concretos, pasos, criterio de aceptación (DoD) y rollback. El workflow de repo ya definido se aplica a cada tarea: typecheck/build → commit descriptivo en español → push a main → deploy automático (Vercel/Render).

1

Reglas del juego

Principios que ordenan el plan
  1. Primero barato, luego estructural. Las victorias de configuración (caché cliente) van antes que los cambios de contrato API (paginación): liberan valor inmediato y no bloquean nada.
  2. Un commit = una tarea. Nada de mezclar refactor con features. Cada tarea termina en producción de forma independiente y reversible (git revert limpio).
  3. Feature-flag mental: la paginación se introduce con page size por defecto alto pero acotado; si algo falla en producción, revert devuelve al comportamiento actual sin migraciones.
  4. Ninguna tarea sin métrica de verificación. Antes/después medible (tabla §5), aunque sea manual con DevTools.
  5. La BD solo gana índices aditivos (CREATE INDEX IF NOT EXISTS): cero migraciones destructivas durante el plan.

Máximo impacto por mínimo riesgo · semana 1
T1Ajustar caché cliente: staleTime + keepPreviousDataP1½ día

Hoy cada query usa staleTime=0: al volver a la pestaña, TanStack Query re-pide gastos, miembros y balances (refetchOnWindowFocus). Objetivo: −60/70 % de peticiones redundantes sin tocar backend.

📁 apps/web/src/pages/group/hooks/useGroupDetail.ts (queries de líneas ~19–70)
  1. Añadir a las queries de lectura ("group", "expenses", "balances", "members") la opción staleTime: 60_000. Las mutaciones no se tocan: sus invalidateQueries siguen forzando frescura tras escribir.
  2. En la query de gastos con filtros, añadir placeholderData: keepPreviousData (import de @tanstack/react-query) para que cambiar filtro no parpadee en blanco.
  3. Verificar con React Query Devtools / pestaña Network: alternar pestañas del navegador y volver → 0 peticiones durante 60 s.
  4. Probar flujo completo: crear gasto → invalidación → refetch inmediato visible en Network.
DoD Volver a una pestaña abierta <60 s genera 0 requests · crear/editar/borrar gasto sigue refrescando listas al instante · typecheck OK.
Riesgo / rollback Mínimo: si un usuario ve datos >60 s antiguos tras editar desde otro dispositivo, bajar staleTime a 15–30 s. Revert = 1 commit.
T2Barrido automatizado de autorizaciónP11 día

La seguridad vive en middleware (requireAuth/requireAdmin/check is_ghost). Objetivo: red de seguridad que falle en CI si una ruta futura olvida el guard. Se reutiliza el patrón Vitest ya existente en shared.

📁 nuevo apps/api/src/tests/authz.test.ts · apps/api/package.json (script "test": "vitest run" + devDep vitest) · helper de arranque de app Fastify exportable desde src/index.ts (extraer buildApp() si no existe)
  1. Refactor mínimo: exportar buildApp() (fabrica de Fastify con plugins/rutas registradas) para poder instanciar la app en tests con app.inject() — sin red, sin BD real (mock de db.ts o SQLite en memoria según acoplamiento).
  2. Crear matriz de perfiles: anónimo (sin JWT), miembro no-admin, ghost promovido ilegalmente, admin.
  3. Escribir tabla de casos: para cada ruta sensible (grupos: roles/borrado; gastos: crear/editar/borrar ajeno; bote; miembros; ghost-members) afirmar 401/403 esperados — incluida la regla «un miembro sin cuenta no puede ser administrador» (routes/groups.ts).
  4. Añadir script npm test al workspace API y documentar en README del repo cómo ejecutarlo.
DoD npm test -w @divido/api verde cubriendo ≥15 rutas × ≥3 perfiles · un test negativo deliberado (quitar requireAdmin) hace fallar la suite (comprobación manual única).
Riesgo / rollback Si mockear BD resulta costoso, alternativa aceptada: tests contra Postgres efímero (contenedor local) marcados como integración; nunca contra Supabase de prod.
T3Paginación server-side de gastos e historialP12–3 días

El cuello nº1. Patrón a replicar: el audit log ya pagina con LIMIT ? OFFSET ? (routes/groups.ts:164–176). Dos endpoints afectados: GET /api/groups/:groupId/expenses (routes/expenses.ts:37) y el feed de group_events.

📁 apps/api/src/routes/expenses.ts · ruta de eventos (groups/events) · packages/shared/src (tipos de respuesta paginada) · apps/web/src/pages/group/hooks/useGroupDetail.ts · componente de lista de gastos/historial en GroupPage.tsx
  1. Contrato compartido primero: en @divido/shared definir Paginated<T> = { items: T[]; total: number; hasMore: boolean }. Compilar shared (npm run build -w @divido/shared).
  2. API: aceptar ?limit=&offset= con clamp seguro (limit ∈ [1,200], defecto 50) y devolver además total vía COUNT(*) sobre la misma cláusula WHERE. Mantener ORDER BY created_at DESC (aprovecha índice existente idx_expenses_group_created).
  3. Compatibilidad: si no llegan query params, responder página por defecto (50) — el frontend viejo simplemente vería menos items; como web y API se despliegan juntas en el mismo push, el riesgo es residual. Aun así, documentar el cambio en el commit.
  4. Web: migrar a useInfiniteQuery con getNextPageParam y botón «Cargar más» al final de Gastos e Historial (mismo componente reutilizable). El acumulado en pantalla sigue creciendo bajo demanda, no de golpe.
  5. CSV/PDF: verificar que la exportación siga viendo TODO el grupo (usar limit=200 iterando páginas en cliente, o parámetro all=1 dedicado solo para export — decisión: preferir bucle en cliente, mantiene la API simple).
  6. Fusionar en este PR el índice CREATE INDEX IF NOT EXISTS idx_events_group_created ON group_events(group_id, created_at DESC) en db.ts (es la T4).
DoD Con un grupo sembrado con 1.000 gastos de prueba: respuesta ≤ ~100 KB por página · «Cargar más» pagina correctamente · CSV exporta los 1.000 · COUNT total correcto · typecheck web+api OK.
Riesgo / rollback Cambia el shape de respuesta → desplegar web+API en el mismo commit (ya es el workflow). Rollback con revert restaura lista completa. Sembrar datos de prueba con script temporal fuera de prod (BD local o grupo desechable).

Preparan la escala real · semana 2
T5Export CSV server-side condicionalP21–2 días

El Blob en cliente bloquea el hilo principal >50k filas. Estrategia: mantener la export en cliente por defecto (coste plano) y añadir vía server solo cuando se supere el umbral.

📁 nuevo endpoint en apps/api/src/routes/exports.ts (ya existe módulo) · BalancesTab.tsx (detección de umbral)
  1. Endpoint GET /api/groups/:id/export.csv?scope=expenses|balances autenticado con requireActiveMember; construir el mismo formato (BOM, separador, escape) que hoy genera el cliente — extraer generador común a @divido/shared para no duplicar lógica.
  2. Responder con streaming: reply.header("Content-Disposition", 'attachment; filename="..."') y escribir por chunks (cursor pg de 1.000 filas) — nunca buffer completo en memoria del servidor.
  3. Cliente: si total > 50_000 (dato que ya devuelve la paginación de T3), navegar al endpoint; si no, mantener Blob local.
  4. Rate-limit específico al endpoint (evitar abusos: export es caro).
DoD Export pequeña idéntica a la actual (diff de bytes salvo timestamp) · con 60k filas simuladas, el navegador descarga sin congelarse y la API mantiene memoria RSS estable (<150 MB).
Riesgo / rollback Doble implementación del formato → evitarla con el generador compartido. El flag es el propio total: revert seguro.
T6Dimensionar pool de conexiones + PgBouncerP2½ día

Prerrequisito para escalar Render verticalmente sin agotar conexiones de Supabase.

📁 apps/api/src/db.ts (creación del pool) · variables de entorno en Render · dashboard Supabase (pooler)
  1. Auditar creación del pool: fijar max: 10, idleTimeoutMillis: 30_000, connectionTimeoutMillis: 5_000 explícitos (no depender de defaults).
  2. Conmutar DATABASE_URL al puerto pooler de Supabase (6543, transaction mode) manteniendo el directo (5432) solo para el DDL de arranque en db.ts.
  3. Probar humo: despliegue → CRUD básico → comprobar en dashboard que conexiones se mantienen ≈ pool max y no crecen.
DoD App funcional vía pooler · número de conexiones acotado bajo carga simulada (k6 rápido: 50 VU × 2 min sin errores 5xx ni «too many connections»).
Riesgo / rollback Transaction mode rompe prepared statements/sesiones: si aparece error prepared statement does not exist, usar session mode (pooler puerto 5432 del pooler) o pg sin statements preparados. Rollback = restaurar DATABASE_URL.
